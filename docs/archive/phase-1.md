# Phase 1 — A trustworthy evaluation: results

Branch: `phase-1-trustworthy-eval`
Base commit: `67c8a90` (head of `phase-0-hygiene-security`)

The point of this phase is to build an evaluation that can be *trusted* **before**
changing the pipeline, so that every later change is judged against a number that
came from this repository. Every figure below is the stdout of the command shown.

### The generator model — a documented substitution

The spec names `llama3.1:8b`. That model is **not installed** on this machine:

```text
$ ollama list
NAME                ID              SIZE      MODIFIED
qwen2.5-coder:7b    dae161e27b0e    4.7 GB    4 months ago
```

The only local model is `qwen2.5-coder:7b`, and the user chose to run the
evaluation with it. Every number below is therefore **`qwen2.5-coder:7b`**, not
the model named in the spec. The runner records the observed model in the JSON.

### The corpus the evaluation runs against

The dev database had been ingested more than once (`procurement_records: 48` for a
24-row corpus), which would have doubled every aggregation answer. The evaluation
therefore runs against an **isolated** corpus at `backend/var/eval-v2/`, ingested
once:

```text
$ $env:DATABASE_URL="sqlite+aiosqlite:///.../backend/var/eval-v2/eval.db"
$ $env:VAR_DIR=".../backend/var/eval-v2/var"
$ $env:LOCAL_STORAGE_DIR=".../backend/var/eval-v2/storage"
$ python -m app.cli ingest "..\data\synthetic" --no-ocr --no-vision

contracts: 3, prices: 15, procurement_records: 24
```

`procurement_records: 24` matches the committed CSV exactly. `purchase_history_2025.csv`
is imported as **structured records** (answered by SQL), not as a retrievable
document — see "Label defect found and fixed" below.

## Oracle-context run

The oracle run injects the labelled documents straight into generation +
verification (retrieval skipped, `retrieval.mode == "oracle"`), so the gap between
it and the baseline is the retrieval's contribution.

```text
mode=oracle  model=qwen2.5-coder:7b  embedding=BAAI/bge-small-en-v1.5
questions=130  duration=646.7s
generation modes: {'llm': 105, 'extractive': 25}

-- retrieval (answerable questions with labelled sources) --
  questions          : 92
  recall@5 / @10     : 0.8913 / 0.8913
  MRR / nDCG@10      : 0.8913 / 0.8913
  page coverage      : 0.8592
  hit rate @5        : 89.1% [81.1%-94.0%] (n=92)

-- answer --
  questions          : 104
  correctness        : 70.2% [60.8%-78.1%] (n=104)
  mean fact coverage : 0.7115

-- refusal --
  precision          : 0.4524
  recall             : 0.7308
  confusion          : tp=19 fp=23 fn=7 tn=81

-- citation --
  questions          : 82
  mean precision     : 0.9004
  no unsupported     : 80.5% [70.6%-87.6%] (n=82)
  verification pass  : 0.9

-- latency (ms, outliers kept) --
  p50=5224.0  p95=7620.0  max=11599.0  mean=4973.7  n=130
```

Read as a diagnosis: even with the right documents supplied, answer correctness is
only **70.2%** and 30 questions still fail — so **most of the loss is not
retrieval**. The oracle's own `recall@10 = 0.8913` is a *label/DB consistency
check*: it means 10% of the labelled (question, document) pairs still do not
resolve inside the oracle, which is why the oracle page coverage is 0.86, not 1.0.

### The dominant bucket is `refusal_failure`, and it is overwhelmingly over-refusal

| | current | oracle |
| --- | ---: | ---: |
| over-refusal (answerable question → refused) | 26 | 23 |
| under-refusal (unanswerable/injection → answered) | 7 | 7 |

Over-refusal is 26 of the 33 current `refusal_failure` rows. The statuses behind it
are `insufficient_evidence` (15) and `partial` (11) — the pipeline abandons or
half-answers questions it could answer. Examples:

```text
v2-price-006  refusal_failure  insufficient_evidence  missing=['310.00']
v2-price-009  refusal_failure  insufficient_evidence  missing=['298.00']
v2-temp-011   refusal_failure  insufficient_evidence  missing=['920.00']
v2-agg-011    refusal_failure  insufficient_evidence  missing=['2000']
v2-compl-006  refusal_failure  insufficient_evidence  missing=['SOC 2']
v2-rel-006    refusal_failure  partial                missing=['J. Alvarez']
v2-mm-008     refusal_failure  partial                missing=['SCANNED EXECUTION COPY']
```

The 7 under-refusals are all `unanswerable` (5) and `security`/injection (2): the
hard-refusal path the spec asks for in Phase 2 does not exist yet.

### Where the pipeline visibly breaks (for Phase 2)

- **Conflicting/superseded prices.** `v2-temp-011` asks for the *original* X200
  price (920.00) and is refused; the pipeline treats the 920.00 / 874.00 pair as a
  conflict instead of version history — exactly the Phase 2 "temporal logic" item.
- **Comparisons answered as "conflicting".** `v2-comp-002/007/009` are labelled
  `generation_error` with `status=conflicting` while the facts (`Net 45`, `Net 30`,
  `DDP`, `FOB`, `ISO 9001`, `SOC 2`) are all in the corpus.
- **Aggregation over structured rows.** `v2-agg-001/008/011` are refused although
  the SQL path holds the answer; `v2-agg-006/007` are `verification_miss`
  (`status=supported` but the number is absent).
- **Citations.** `no unsupported = 16.3%` at baseline: the displayed citation list
  is mostly not the supporting chunks.
- **Latency.** p50 8691 ms vs the < 5000 ms target; the pipeline is sequential.

## Label defect found and fixed

While validating the labels against the database I found that all 12 aggregation
questions pointed `expected_documents` at `purchase_history_2025.csv`:

```text
labelled documents NOT present in the DB:
   12x purchase_history_2025.csv
affected questions: v2-agg-001 … v2-agg-012
```

That CSV is imported as **structured records**, never as a document, so those
labels could never be satisfied and were inflating the retrieval denominator (104
instead of 92) and the `retrieval_miss` count. The 12 questions were corrected to
carry no document label (answered by SQL) with a note explaining why. After the
fix:

```text
labelled documents NOT present in the DB:
total missing pairs: 0
```

All figures in this document are from the corrected labels.

## Known limitations (not hidden)

- **Optional LLM-judge not implemented.** The spec marks the rubric judge + 30-sample
  human-agreement script optional; it was not built. Correctness here is exact
  `expected_facts` substring matching, which is deliberately conservative (it will
  mark a correct-but-differently-worded number as missing).
- **No stronger-model comparison.** Only `qwen2.5-coder:7b` is installed, so the
  "one stronger model if configured" run could not be produced.
- **The oracle is document-level, not page-level.** It supplies all chunks of the
  labelled documents (labelled pages first). It therefore does not isolate
  "wrong page selected"; the 0.86 page coverage is the residual of that.
- **Cost is `None`.** No per-token price is configured for the local model, so the
  runner reports `cost_note` rather than inventing a rate.
- **The 45.6 s latency max is cold start** (question 1 loads the model); the p50 is
  the honest steady-state figure.

$env:DATABASE_URL="sqlite+aiosqlite:///<repo>/backend/var/eval-v2/eval.db"
